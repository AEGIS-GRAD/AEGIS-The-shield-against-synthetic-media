## 1. Executive Summary & Problem Definition

AEGIS establishes multi-modal synthetic media defense across both offline file evaluation and real-time surveillance. While offline file evaluation operates in a single-pass paradigm resulting in a static `CourtAdmissibleVerdict`, **live surveillance** operates under continuous streaming constraints (25–30 FPS per camera) over persistent mTLS sessions.

When an anomaly or attack is detected on an active surveillance stream—such as deepfake face replacement, replay injection, or foreign sensor spoofing—simply severing the network connection or logging an ephemeral alert to standard output fails legal standards. In forensic investigation and criminal prosecution, evidence must withstand judicial scrutiny:
1. **Chain of Custody (Provenance):** Unambiguous proof of the origin camera device (mTLS X.509 certificate, serial, network endpoint), exact receiving interface, and UTC millisecond timestamp.
2. **Mathematical Tamper-Evidence (Integrity):** Cryptographic verification that stored frames, sensor metrics, and analyst notes were not altered, backdated, or fabricated after acquisition.
3. **Multi-Signal Admissibility (Substance):** Raw pixel arrays, cryptographic hash states, hardware sensor fingerprints (PRNU PCE), and AI model inference metrics bound together in an auditable bundle.

This specification details the architecture of the **AEGIS Surveillance Forensic Evidence Vault** (`SurveillanceEvidenceVault`), an append-only, content-addressed, hash-chained evidence storage engine for live-surveillance incidents.

## 2. Regulatory & Legal Admissibility Foundations

The architecture strictly adheres to three digital evidence preservation standards:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        LEGAL COMPLIANCE PILLARS                        │
├─────────────────────────┬────────────────────────┬─────────────────────┤
│    ISO/IEC 27037:2012   │  NIST SP 800-61 Rev. 2 │ FRE Rule 902(13/14) │
├─────────────────────────┼────────────────────────┼─────────────────────┤
│ Digital Evidence        │ Incident Response &    │ Self-authenticating │
│ Identification,         │ Handling: Immediate    │ electronic records: │
│ Collection, Acquisition,│ Preservation, Triage,  │ Certified process,  │
│ and Preservation.       │ & Forensic Containment.│ hash verification.  │
└─────────────────────────┴────────────────────────┴─────────────────────┘
```

1. **ISO/IEC 27037:2012 Principles:**
   - **Auditability:** Every transaction, read, and write within the vault is immutable and deterministic.
   - **Repeatability:** Independent third-party forensic tools must be able to verify all cryptographic hashes, PRNU correlation peaks, and model inference outputs using the stored data.
   - **Preservation:** The original evidentiary frames are stored bit-for-bit in uncompressed or lossless formats alongside their SHA-256 digests.

2. **Federal Rules of Evidence (FRE) Rule 902(13) & (14):**
   - Certified records generated by an electronic process or system that produces an accurate result, confirmed by a certified digital signature and hash chain.

## 4. Architectural Design: The Three-Tier Storage Vault

To achieve sub-millisecond write latency without blocking 30 FPS ingestion while maintaining absolute tamper-evidence, the vault implements a three-tier architecture:

```
                            INCIDENT TRIGGER EVENT
                 (Hash Break, PRNU PCE < 50, Deepfake Breach)
                                       │
                                       ▼
    ┌────────────────────────────────────────────────────────────────────┐
    │                 Tier 1: Non-Blocking Memory Ring                   │
    │  • Zero-copy frame buffer clone                                    │
    │  • Async queue handoff to disk worker worker task                  │
    └──────────────────────────────────┬─────────────────────────────────┘
                                       │ (Async Handoff < 0.2 ms)
                                       ▼
    ┌────────────────────────────────────────────────────────────────────┐
    │             Tier 2: Content-Addressed Blob Storage (CAS)           │
    │  • Root: `vault/blobs/<sha256[:2]>/<sha256>.png`                   │
    │  • Lossless raw image frame + context window snapshots             │
    │  • Immutable permissions (POSIX 0444 WORM)                         │
    └──────────────────────────────────┬─────────────────────────────────┘
                                       │
                                       ▼
    ┌────────────────────────────────────────────────────────────────────┐
    │          Tier 3: Cryptographically Chained Evidence Ledger         │
    │  • Incident Manifest: `vault/incidents/<incident_id>.json`         │
    │  • Append-Only Audit Ledger: `vault/ledger.jsonl`                  │
    │  • Chain Hash: H_k = SHA256(H_{k-1} || Record_Payload)             │
    │  • Signed by Ingestion Gateway Ed25519 / HMAC Key                  │
    └────────────────────────────────────────────────────────────────────┘
```

### 4.1 Content-Addressed Blob Storage (CAS)
Evidence images are stored indexed by their SHA-256 cryptographic digest:
$$\text{Storage Path} = \texttt{vault/blobs/} \parallel H(F)[:2] \parallel \texttt{/} \parallel H(F) \parallel \texttt{.png}$$
- **Deduplication:** Repeated identical frames share the same immutable blob.
- **Intrinsic Verification:** The filename itself is the cryptographic ground truth. If any byte within the image is modified, `SHA256(file) != filename`, immediately flagging corruption.

### 4.2 Append-Only Cryptographic Ledger
Every incident appended to the vault updates the ledger chain:
$$H_0 = \text{GENESIS\_HASH} = \text{SHA256}(\texttt{"AEGIS\_VAULT\_V1\_GENESIS"})$$
$$H_k = \text{SHA256}\left(H_{k-1} \parallel \text{IncidentID}_k \parallel \text{Timestamp}_k \parallel \text{ManifestDigest}_k\right)$$

This structure guarantees:
- **No Deletion:** Removing incident $k$ breaks the hash link between $k-1$ and $k+1$.
- **No Insertion:** Splicing a fake record requires recomputing all subsequent hashes.
- **No Backdating:** Timestamp monotonic progression is validated along the chain.

## 6. Implementation Architecture

The core Python module is located at [security/forensics/evidence_vault.py](file:///g:/College/Graduation%20Project/AEGIS-The-shield-against-synthetic-media/security/forensics/evidence_vault.py).

### 6.1 Key Methods
- `store_incident(...) -> IncidentRecord`: Captures frame bytes, computes SHA-256 digests, stores blobs, writes incident manifest, appends chained ledger entry, and returns the sealed record.
- `verify_vault_integrity() -> VaultAuditResult`: Traverses every record from genesis to latest, validates internal hash consistency, verifies blob presence and bit integrity, and reports any tampered or missing entries.
- `export_incident_package(incident_id, output_zip) -> Path`: Bundles manifest, raw image blobs, chain certificates, and an ISO/IEC 27037 verification script into a legally portable archive.

## 7. Performance & Resource Constraints

1. **Write Latency:** Disk I/O must not impede network packet processing. Framing and blob writes use asynchronous thread pools (`asyncio.to_thread` / `concurrent.futures.ThreadPoolExecutor`), bounding event-loop delay to $< 0.5\text{ ms}$.
2. **Storage Quota & Retention:**
   - Alerts store keyframe PNGs (~200 KB) and context window frames.
   - 1,000 critical security incidents require $< 250\text{ MB}$ of storage.
   - Ledger integrity is independent of volume size due to streaming forward verification.
